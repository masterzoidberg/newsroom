# Completion strategy

## Objective and constraints

Finish the smallest reliable daily-use product around the existing evidence core. No application code changed in this audit. Preserve runtime data, offline operation, provenance, backward-compatible evidence access and frozen value experiments. No paid calls without authorization. No completion percentage or fixed finish date is defensible from this audit.

## Milestones and order

| Milestone | Tasks | Exit condition |
|---|---|---|
| M0 Trustworthy baseline | AST-01 | current HEAD, isolated dev/rehearsal roots and reproducible checks; CI portability defect addressed |
| M1 Start Newsroom | AST-02–05 | one authority, ownership/port handling, bounded lifecycle, status and shortcut/sign-in recovery |
| M2 Real provider settings | AST-06–11 | shared public configuration, secure credential storage, durable budget, reload, explicit validation and functional Settings |
| M3 Daily-use workflows | AST-12–15 | no-ID Watch setup, dark/mobile correction, recovery controls, representative content-quality evidence |
| M4 Value verdict | AST-16–18 | sufficient unchanged/segmented observation, valid comparison, human scoring and explicit scope verdict |
| M5 Qualified release candidate | AST-19–20 | installed Windows/mobile acceptance and evidence-backed simplification |
| Conditional extensions | AST-21–22 | useful paid Ask if justified; small commercial pilot only after value and release gates |

Default execution follows task number except the already-running observation: **AST-16 continues operationally in parallel with isolated engineering, without spawning work or changing the trial automatically.** Its calendar duration cannot be accelerated by adding features. AST-17 can prepare its eligible snapshot after AST-01, independently of the observation's calendar, but cannot run paid comparisons without authorization. AST-19 preparation can occur on an isolated candidate before value acceptance; its final DONE requires the value/scope verdict.

Startup comes before credential implementation because Windows user/session ownership determines credential availability. Shared metadata and durable budgets come before enabling new paid paths. UI provider completion initially covers the capability already supported—Article Analysis—while clearly showing other routes as local. This is faster and more honest than making a global provider switch that is not used by Ask/research.

Do not delay ownership/startup, secure settings or obvious onboarding defects until a market study. These are explicit owner requirements. Do delay speculative capability expansion and commercial infrastructure. Preserve the existing trial separately so engineering can progress without moving its success criteria.

This is deliberately conservative sequencing for one primary task at a time, not a claim that every coding edit is technically coupled. If execution proves a smaller safe reorder, record it in DECISIONS and update the ledger/prompts together.

## Checkpoints

After AST-05: repeat launch, conflict, stop, crash and sign-in recovery against a temporary installation; no provider implementation before user/session identity is settled.

After AST-11: fake-provider special acceptance proves one config authority, secret absence, budget enforcement, worker reload and removal. A paid live call remains a separate authorized validation, not a default development step.

After AST-15: run local full-chain fixture plus representative content-quality checks and browser flow. File only demonstrated defects; preserve saturation/refusal until evidence justifies a specific repair.

After AST-18: use the actual KEEP/SIMPLIFY/CONTEXTUALIZE/DEFER/REMOVE verdict to select release scope. Inconclusive evidence is a valid blocked release-value gate, not an excuse to invent scores.

## Risk and rollback strategy

The highest risks are duplicate process ownership, credential/session mismatch, non-atomic credential+metadata updates, spending races across reloads, and contaminating the live trial. Address each with early isolated failure tests. Additive metadata migrations must preserve schema-36 upgrades; old evidence migrations are never rewritten. Code rollback and data rollback are separate operations. Any new task spanning unrelated subsystems must be split before editing; do not use this plan to authorize a rewrite.
