# PHASE 29.6 — STORY TIME-SEMANTICS BASELINE CLOSURE

## Status and boundary

Phase 29.6 is a surgical engineering closure for Story source-time semantics.
It fixes the known Phase 29/29.5 baseline defect without adding product
features, changing Story ranking, weakening temporal matching, or beginning
Phase 30.

## Starting defect and root cause

The incoming automatic Story candidate already used the source-time rule
`published_at or document_version.retrieved_at`. Existing Story candidates
reconstructed only `documents.published_at`; when publication time was absent,
the shared comparison fell back to `stories.created_at`. A Story created days
after its source document was retrieved therefore appeared outside the strict
72-hour window even when the incoming Claim, proposition, and text were exact
matches.

The pre-fix cross-promotion reproduction showed `claim_exact_match=True`,
`text_overlap=1.0`, and `time_compatible=False`, producing `no_match` and a
second Story. The other two known failures were downstream consequences of the
same incorrect Story identity resolution.

## Timestamp invariant and implementation

For every source document used in Story resolution, the effective document
time is:

```text
documents.published_at OR MIN(document_versions.retrieved_at)
```

Publication time remains authoritative when present. Otherwise the earliest
canonical retrieval is used. The earliest retrieval is derived per document
through an aggregate, while the current/latest version remains the single
logical document row used for current metadata. Story creation time remains a
lifecycle/audit timestamp and is no longer a source-time fallback.

The shared current-Story document query now carries both the selected current
version retrieval time and the stable `first_retrieved_at`. The automatic
candidate query derives the same aggregate and uses the same effective-time
helper. Existing Story candidates and incoming candidates therefore reach the
same temporal compatibility gate without changing the 72-hour window.

No migration was required; schema remains 36.

## Regression tests

`tests/test_phase296_story_time_semantics.py` adds deterministic coverage for:

- a Story processed more than 72 hours after source retrieval remaining
  compatible with an equivalent incoming Claim;
- a document with first retrieval August 20 and a later version August 24
  remaining one logical current document whose fallback time is August 20;
- publication time taking precedence over retrieval time; and
- both the automatic candidate path and the Story evolution candidate path
  using the stable source time.

## Downstream closure

All three baseline failures pass without expectation changes:

- `test_cross_promotion_concurrency_re_resolves_after_first_story_creation`;
- `test_second_accepted_claim_creates_one_revision_with_exact_sorted_claim_set`;
- `test_multiple_rules_and_later_revision_remain_distinct_while_revision_n_isolated`.

The corrected Story re-resolution causes the intended Claim set, Report
revision lineage, and Alert revision isolation to be restored.
