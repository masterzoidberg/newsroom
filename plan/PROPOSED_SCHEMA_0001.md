# Proposed Standalone Schema — Migration 0001

Status: **Proposal for architectural review. Not yet implemented.**
Product authority: `plan/STANDALONE_NEWSROOM_PRODUCT_SPEC.md`
Phase-0 evaluation contract: `newsroom.evals` (see `docs/EVALUATION.md`)

This document specifies the intended first-release schema so it can be reviewed
before any migration is written. It does **not** create the migration. Nothing
here is applied to a database.

## 0. Conventions

- SQLite, WAL, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`.
- IDs are stable, opaque, application-generated strings (e.g. `cat_<hex>`,
  `st_<hex>`), never integers, never reused, never user-renamed.
- Timestamps are ISO-8601 UTC strings (`TEXT`), seconds precision, generated by
  application code (not SQLite defaults) so behavior is identical across tests.
- Booleans are `INTEGER` `0/1` for SQLite compatibility, with `CHECK ... IN (0,1)`.
- Enums are `TEXT` with `CHECK` constraints. The `newsroom.evals` and schema
  validation modules remain the single source of truth for enum membership.
- Soft delete = `deleted_at TEXT` (`NULL` = live). Hard delete is reserved for
  small child rows and pure join rows where history has no value.

storage of full article bodies is **not** required; `content_kind`/`normalized_json`
permit minimal permitted snapshots for replay only.

### claim_evidence

| column       | type    | constraints                          |
|--------------|---------|--------------------------------------|
| id           | TEXT    | PRIMARY KEY                          |
| claim_id     | TEXT    | NOT NULL REFERENCES claims(id) ON DELETE CASCADE |
| evidence_span_id | TEXT | NOT NULL REFERENCES evidence_spans(id) ON DELETE CASCADE |
| relationship | TEXT    | NOT NULL CHECK (relationship IN ('supports','contradicts','contextualizes')) |
| created_at   | TEXT    | NOT NULL                             |
| UNIQUE(claim_id, evidence_span_id, relationship) | |                     |

**Why:**
- **Accepted Claim immutability:** accepted Claim `proposition` text is never
  edited. A materially corrected proposition is a *new* Claim whose
  `supersedes_claim_id` points at the old one. Only `state` (and derived fields)
  change, with history in `claim_state_history`.
- **Claim-state history:** every state transition is a row; `unsubstantiated`
  means "lacks sufficient support", never "false". Contradiction is represented
  by `claim_evidence` rows with `relationship='contradicts'`.
- **Supersession:** `supersedes_claim_id` is a self-FK forming a chain.
- **Evidence Span locator/hash:** `locator_type`/`locator_value` pin the exact
  place (paragraph, section, offset, JSON pointer, page). `span_hash` is a
  deterministic hash of the excerpt + locator so a span can be re-found and
  integrity-checked against the frozen DocumentVersion.
- Source quality (`sources.default_quality`) and evidence relationship are
  separate concepts and never combined into Claim state.

### monitors

| column       | type    | constraints                          |
|--------------|---------|--------------------------------------|
| id           | TEXT    | PRIMARY KEY                          |
| target_type  | TEXT    | NOT NULL CHECK (target_type IN ('topic','subject','story','source','research_question')) |
| target_id    | TEXT    | NOT NULL                             |
| policy_id    | TEXT    | NOT NULL REFERENCES monitoring_policies(id) |
| enabled      | INTEGER | NOT NULL DEFAULT 1 CHECK IN (0,1)    |
| next_check_at| TEXT    | NULL                                 |
| last_run_at  | TEXT    | NULL                                 |
| last_result  | TEXT    | NULL                                 |
| created_at   | TEXT    | NOT NULL                             |
| updated_at   | TEXT    | NOT NULL                             |
| UNIQUE(target_type, target_id)         |        |                                  |

**Why (Monitor target polymorphism without destroying referential integrity):**
`target_type` + `target_id` is a polymorphic reference. To preserve integrity we
do **not** rely on a bare `target_id`. Instead: (a) `target_type` is a closed
enum; (b) `UNIQUE(target_type, target_id)` prevents duplicate monitors for one
target; (c) integrity is enforced in application code inside a single write
transaction (create/delete the target and its monitor atomically) rather than
with a composite FK — SQLite cannot enforce a polymorphic FK. Documented
trade-off: this is the one place a soft polymorphic reference is accepted,
guarded by the closed enum and transactional writes.

## 11. Resolution of the required design questions

1. **Source vs Document vs DocumentVersion** — three distinct entities (see §4).
   `sources` = origin; `documents` = canonical item; `document_versions` =
   retrieved snapshot. Evidence → `document_versions` only.

2. **Evidence Span locator and hash strategy** — `locator_type`/`locator_value`
   for placement, `span_hash` for integrity; `UNIQUE(document_version_id, span_hash)`.

3. **Accepted Claim immutability** — `proposition` immutable once `accepted_at`
   is set; corrections create a new Claim with `supersedes_claim_id`.

4. **Claim-state history** — `claim_state_history` append-only, one row per
   transition with reason.

5. **Claim supersession** — self-FK `claims.supersedes_claim_id` chain.

6. **Story revision semantics** — prose on immutable `story_revisions`; review on
   `story_review`; `revision_number` monotonic per Story.

7. **Last-reviewed revision tracking** — `story_review.last_reviewed_revision_id`.

8. **Monitor target polymorphism** — closed `target_type` enum + `UNIQUE(target_type,
   target_id)` + transactional writes; no composite polymorphic FK.

9. **Job leases / retry state** — `jobs.lease_owner`/`lease_expires_at` +
   atomic claim; `job_attempts` records each attempt; bounded by `max_attempts`.

10. **Research Question origin** — `origin_type` + `origin_id` (soft reference,
    same reasoning as monitors).

11. **Provider-neutral acquisition provenance** — `monitoring_policies.allowed_channels`
    and `provider_usage.capability` use capability names; provider names are
    metadata only.

12. **Cost attribution** — `provider_usage` links to `job_id`/`monitor_id`/
    `research_question_id` and records units/cost.

13. **Persistent content policy** — full article bodies are not persisted by
    default; `document_versions.content_kind` allows `metadata`/`excerpt`/
    `full_text` and `normalized_json` stores only what is permitted and needed
    for replay. See `docs/EVALUATION.md` for the fixture content policy.

14. **Soft vs hard delete** — Categories/Topics/Subjects/Sources/Stories/
    ResearchQuestions are soft-deleted (`deleted_at`). Topic terms, aliases,
    join rows, and evidence spans are hard-deleted (no valuable history).
    Claims are never deleted (superseded), preserving the ledger.

15. **Stable slugs** — slugs are `UNIQUE` and never change on rename; they are
    identity keys for Categories/Topics/Sources. Renaming updates `name` only.

## 12. Open architecture questions for review

1. Should `monitors.target_id` integrity be further hardened with per-target
   trigger validation (a CHECK with a subquery is not supported by SQLite), or is
   transactional application enforcement + the closed enum sufficient?
2. Should `provider_usage.provider` be normalized into a `providers` table, or is
   it acceptable as free text metadata in migration 0001?
3. Is `story_review` (1:1 with `stories`) the right shape, or should review be a
   per-revision concept with "current" derived by query?
4. Should `evidence_spans.span_hash` be a content hash of `excerpt` alone, or of
   `excerpt + locator_type + locator_value`? (Recommendation: both are stored;
   the uniqueness key uses excerpt+locator.)
5. Should full-text `normalized_json` on `document_versions` be deferred to a
   later migration to keep 0001 minimal?

## 13. Recommendation

Adopt this schema as migration 0001 with the following defaults:

- No `providers` table yet (keep `provider` as metadata text).
- Enforce `monitors`/`research_questions` polymorphic integrity in application
  transactions, documented as a deliberate deviation from strict FK coverage.
- Defer full-text persistence (kept as permitted snapshots for evaluation only).
- Keep Claims hard-immutable and never deleted; supersede instead.

This schema is sufficient to represent the first-release domain and the Phase-0
evaluation contract without locking in provider or vector infrastructure.
